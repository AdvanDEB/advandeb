## 0. Executive Summary

AdvanDEB is, on the inside, a substantive multi-component research platform:
five Python ReAct agents behind a Rust MCP gateway, a FastAPI backend with
WebSocket-streaming chat, a Vue 3 + Cosmograph KB visualizer, and a real
ingestion pipeline that has already processed ~1300 papers and seeded 1236
stylized facts. The architecture documents (`SYSTEM-OVERVIEW.md`,
`ARCHITECTURE-REVISION.md`, `ROADMAP.md`) are coherent, and the runtime topology
in `RUNNING.md` matches what is on disk.

From the outside, almost none of that is visible. **The deployed site at
https://advandeb.com presents only a Vue SPA shell behind a login wall.** An
unauthenticated researcher landing on the domain sees a title, a sign-in form,
and nothing else — no project description, no domain context, no example
graphs, no docs, no contact, no SEO metadata. The platform is hidden behind
auth even for read-only knowledge browsing, which contradicts the project's
own goal of disseminating curated biology knowledge.

Inside the code there are also concrete defects to fix before any external
launch:

- A **JWT type-confusion bug**: refresh tokens are accepted as access tokens
  on every protected route (auth.py vs core/auth.py — see §3.2).
- Two **broken test files** (`tests/test_graph_service.py`,
  `tests/test_chat_service.py`) reference modules/methods that no longer
  exist; the test suite does not collect cleanly.
- Configuration **drift** between `core/config.py` defaults and `.env.example`
  (MCP port 3000 vs 8080; OAuth redirect port 8000 vs 8400).
- **96 occurrences of `datetime.utcnow()`** — deprecated in Python 3.12 and
  scheduled for removal; the project pins Python 3.11 but conda environments
  may upgrade.
- **`/health` is shadowed by the static SPA** on production (returns
  `index.html`, not JSON) — production monitoring claims in README are
  effectively dead.
- **Several large godfiles** (1500+ lines): `app/kb/pipeline.py` (1523),
  `knowledge-builder/services/graph_query_service.py` (1625), agents at
  ~950 lines each.
- **No public-facing landing/marketing content, no SEO, no `robots.txt`
  semantics, no OpenGraph** — the site is invisible to search and to
  drive-by visitors.

None of this is fatal. The architectural backbone is sound and the data is
real. What is missing is the last 10% that converts a working internal
platform into a credible public research tool. The plan in §11 below lays
out the change set in priority order.

## 2. Public website review — https://advandeb.com

The site is deployed (Cloudflare in front, `cf-ray` headers present) and the
SPA loads. The findings below describe what an unauthenticated visitor sees.

### 2.1 What renders for an anonymous visitor

- Page title: `AdvanDEB Modeling Assistant`.
- Body before JS hydration: a single empty `<div id="app"></div>`.
- After hydration: `HomeView.vue` shows the H1 *"AdvanDEB Modeling Assistant"*,
  the line *"Main platform GUI for knowledge building and modeling"*, and a
  single blue **Login with Google** button. Nothing else.

That's the entire public surface. There is no:

- Project mission, abstract, or DEB explainer
- Screenshots or example knowledge graphs
- "How it works" / pipeline diagram
- Roadmap or status
- Team / institution / contact
- Documentation links
- Public read-only graph or fact browser
- Footer with license, repository link, or imprint
- Cookie/consent notice (likely required if you ship to EU)

### 2.2 SEO, accessibility, performance

- **No `<meta name="description">`**, no OpenGraph (`og:title`, `og:image`),
  no Twitter cards, no `<link rel="canonical">`, no JSON-LD.
- **No SSR / no prerender** — Googlebot can usually render SPAs but
  Bing/DuckDuckGo and most academic-indexing bots cannot. For a research
  platform this is a discoverability problem.
- **No `robots.txt` content tested** (worth verifying).
- **No `sitemap.xml`**.
- **Favicon** is referenced but not verified.
- HTML response is small (`<700 bytes` before assets) which is fine, but
  the JS bundle and Cosmograph vendor chunks (`cosmos-vendor-*.js`) are
  loaded on every route, including login — wasted bandwidth for users
  who never see the graph.

### 2.3 Public endpoints exposed

- `GET /api/auth/config` → `{"google_oauth_enabled": true}` (public, OK).
- `GET /health` → **returns the SPA's `index.html`**, not JSON. The route
  is defined in `main.py:171` but the production deployment (Cloudflare or
  upstream proxy) seems to route only `/api/*` to the FastAPI app and
  serve the SPA bundle for everything else. The `/health` endpoint
  advertised in `RUNNING.md` and `app/README.md` is therefore not
  reachable for external monitoring.
- `GET /api/kb/viz/schemas` → 401 (correctly requires auth).

### 2.4 Login / auth UX

`LoginView.vue` is a serviceable form (email/password + optional Google),
but:

- The closing hint reads *"Don't have an account? Contact an administrator."*
  with no contact link, no email, no signup CTA.
- The Google client ID is read from `import.meta.env.VITE_GOOGLE_CLIENT_ID`.
  If that build-time env was not set, the button is shown but the OAuth
  URL is malformed (`client_id=undefined`). There is no runtime guard.
- After a failed Google callback the user sees the error inline, but on
  success the page navigates to `/` without clearing the `?code=` query
  parameter from history — refresh re-submits the (now consumed) code.

### 2.5 Branding & visual design

The styling is the bare Vite scaffold (system font stack, hairline borders,
inline CSS in each `.vue` file). There is no design system, no theme
tokens, no dark mode. The Element Plus dependency is listed in
`package.json` but `LoginView` and `HomeView` do not use it — usage is
ad-hoc per-component.

## 3. Backend (app/backend) — code review

### 3.1 What's good

- Clear separation: `core/` (cross-cutting), `api/routes/` (HTTP),
  `services/` (business logic), `clients/` (external), `kb/` (pipeline).
- `core/database.py` cleanly documents the three data stores
  (app MongoDB, KB MongoDB workflow metadata, ArangoDB knowledge).
- Indexes are created idempotently in `ensure_app_indexes()`.
- Background-task singleton election (`_is_primary_worker`) is at least
  thought about — comments are honest about its fragility.
- WebSocket chat (`/ws/chat/{session_id}`) handles JWT-in-query-param
  cleanly, including the 4401 close-code convention so the browser sees
  a structured failure.
- File logging via `RotatingFileHandler` is configured early.

### 3.2 Bugs and defects

| # | Severity | Location | Issue |
|---|---|---|---|
| B1 | **High** | `core/auth.py:39-49` + `get_current_user` | `verify_token` does not check `type`. A **refresh token** therefore passes `Depends(get_current_user)` and authenticates any protected endpoint. Only `/api/auth/refresh` checks `payload["type"] == "refresh"`. Mitigation: enforce `payload.get("type") != "refresh"` in `get_current_user` (and ideally tag access tokens with `type: "access"` explicitly). |
| B2 | **High** | `core/auth.py:66` | `ObjectId(user_id)` is unguarded — a JWT with a malformed `sub` raises `bson.errors.InvalidId` → FastAPI returns 500 instead of 401. |
| B3 | High | `api/routes/auth.py:127-131` | The bare `except Exception as e` returns `f"Authentication failed: {str(e)}"` to the client. Leaks Google SDK internals on failure. |
| B4 | High | `services/user_service.py:98-112` | Timing-oracle: `authenticate_user` returns immediately if the user is absent (`return None`), but performs bcrypt verification if present. Response time leaks user existence. Always run bcrypt against a dummy hash on miss. |
| B5 | High | `core/config.py:56` vs `.env.example:40` | `MCP_SERVER_URL` default is `http://localhost:3000` in code but `.env.example` sets it to `8080`. If `.env` is missing the var, the backend talks to the wrong port. |
| B6 | High | `core/config.py:32-36` vs `.env.example:23` | `GOOGLE_REDIRECT_URI` example points to `localhost:8000`, but the backend runs on `8400`. Same drift as B5. |
| B7 | Medium | `tests/test_graph_service.py` | Imports `app.services.graph_service.GraphService` — that module has been **deleted** (only stale `.pyc` files remain). Test fails on collection. |
| B8 | Medium | `tests/test_chat_service.py` | Patches `svc._get_mcp_response` and expects the string `"placeholder"` for `MCP_SERVER_ENABLED=False`. The current `send_message` has no such method and returns `"MCP server is not enabled."`. Tests are stale by ≥1 refactor. |
| B9 | Medium | `main.py:199` | The catch-all `@app.get("/{full_path:path}")` shadows `/health` in production deployments that don't whitelist `/health` separately at the proxy. `/health` is essentially dead in prod. |
| B10 | Medium | `services/chat_service.py:34` | Hard-coded `_CHATBOT_AGENT_WS = "ws://localhost:8086"`. Should be `settings.CHATBOT_AGENT_WS`. Couples the app to a single-host deployment. |
| B11 | Medium | `clients/mcp_client.py` | A new WebSocket connection is opened **for every call** (`call_tool`, `stream_tool_call`). Per-request connect + handshake under chat load. No reuse. |
| B12 | Medium | `core/auth.py` + `services/*` | 96 occurrences of `datetime.utcnow()` across `app/` and `knowledge-builder/`. Deprecated in Python 3.12 (`DeprecationWarning: datetime.utcnow() is deprecated`). Should be `datetime.now(timezone.utc)`. |
| B13 | Low | `api/routes/auth.py:181-184` | `/logout` is a no-op stub with a TODO; tokens remain valid until expiry (1h access / 30d refresh). For a research portal that's acceptable, but document it. |
| B14 | Low | `api/routes/documents.py:46-54` | `POST /documents/upload` accepts `UploadFile` with no size cap or MIME validation at the route. Pushed entirely into `UserSubmissionService` — needs verification that bounds are enforced there. |
| B15 | Low | `main.py:130` | `ProxyHeadersMiddleware(trusted_hosts="*")` trusts forwarded headers from anywhere. Fine while the only ingress is your own nginx/Cloudflare, but worth narrowing to the proxy IPs. |
| B16 | Low | `services/user_service.py:152-173` | `assign_role` / `remove_role` skip the role-name vocabulary check — any string can be written into `users.roles`. Add a whitelist. |

### 3.3 Architecture concerns

- **`app/kb/pipeline.py` is 1523 lines** — covers PDF jobs, KG linking,
  GPU-aware concurrency estimation, Ollama probing, and ChromaDB
  embedding. It should be split: `pipeline/concurrency.py`,
  `pipeline/pdf_job.py`, `pipeline/kg_link.py`, with thin glue.
- **Sync ArangoDB driver wrapped in a global 2-worker thread pool**
  (`visualization.py:23`, `provenance_service.py:18`). Under concurrent
  KB users this is the dominant bottleneck. Either:
  - Move to `python-arango-async` (preview), or
  - Raise the pool size and audit thread-safety of the singleton client.
- **`Settings` lacks production guardrails** — no validator on
  `JWT_SECRET_KEY` to reject the default `"your-secret-key-here-…"`
  string when `ENVIRONMENT != "development"`. A misconfigured deploy
  silently runs with the example secret.
- **CORS** is correctly origin-listed, but `allow_methods=["*"]`,
  `allow_headers=["*"]`, `allow_credentials=True` is permissive — fine
  for now, but credential-bearing wildcard methods/headers should be
  narrowed.
- **Worker-id heuristic** (`_is_primary_worker`) acknowledges in its
  own docstring that it's "an approximation". With the current single
  uvicorn process this is moot, but if you ever move to gunicorn workers
  the rebuild queue could double-fire or never fire. Use a real lease in
  MongoDB (a `singleton_locks` collection with TTL) instead.

### 3.4 Test coverage

- 2 backend test files, both broken (B7, B8). Effective backend coverage
  through pytest is currently zero.
- `knowledge-builder/tests/` has 6 files (models, taxonomy, chat models,
  agent pipeline, ingestion, sf_seed) — not exercised in this review,
  but they at least import current modules.
- `tests/integration/test_smoke.py` exists at repo root — worth verifying
  it still runs against the live stack.
- No CI configuration is present in `.github/`, `.gitlab-ci.yml`, etc.
  (none found).

## 5. knowledge-builder (`advandeb_kb`) — code review

### 5.1 What's good

- The agent layer has a real `base_agent.py` + `react_engine.py` core,
  not just a pile of one-off scripts.
- Services are functionally cohesive — each addresses a single
  responsibility (chunking, embedding, chromadb, evidence registry,
  reference verifier, taxonomy, …).
- ArangoDB is the canonical KB store with MongoDB only for ingestion
  workflow state — this split is documented in
  `app/backend/app/core/database.py` and matches reality.

### 5.2 Issues

- **`services/graph_query_service.py` (1625 LOC)** and
  **`agents/react_engine.py` (952 LOC)** and **`agents/chatbot_agent.py`
  (946 LOC)** are godfiles. They are the heart of the system, which makes
  them the highest-risk files to refactor — but also the ones that most
  need it. Suggested splits:
  - `graph_query_service`: per-schema query builders + a thin facade.
  - `react_engine`: prompt construction, tool dispatch, trace
    serialization in separate modules.
  - `chatbot_agent`: server framing (WebSocket JSON-RPC) separate from
    pipeline logic.
- **Two different `Settings` objects**: `advandeb_kb.config.settings`
  and `app.core.config.settings`. They drift independently — e.g.
  `OLLAMA_BASE_URL` exists in both, and `OLLAMA_MODEL` exists only in
  the KB one but is read by `app/kb/pipeline.py:101`. There is no
  single source of truth.
- **`knowledge-builder/README.md`** is out of date — describes a
  standalone backend on port 8000, references a `setup.sh` that doesn't
  exist, and presents the package as a self-hosted product rather than
  an embedded library. Per `docs/SYSTEM-OVERVIEW.md`, KB is now a
  *toolkit*. Reconcile.
- **Five top-level test files** at the package root
  (`test_agents_basic.py`, `test_agent_server.py`,
  `test_embedding_pipeline.py`, `test_kg_builder.py`) plus a `tests/`
  directory. Consolidate into `tests/` so `pytest` collects them
  automatically.

### 5.3 Pipeline status

Memory note: 1306 ingestion jobs queued, ~100+ completed, 3 concurrent
Ollama workers, sf_support graph rebuilt at 3373 nodes / 2243 edges.
This is the live state at last record — re-verifying actual numbers
should be one of the first acts of the next session.

## 6. mcp/ (Rust gateway) — code review

### 6.1 What's good

- 2845 LOC, well-modularized:
  `gateway/{registry,router,pool,balancer,circuit_breaker,retry}.rs`,
  `mcp/{protocol,server}.rs`, `workflow/{context,executor}.rs`.
- Documented Prometheus metrics, optional TLS via `rustls`, env-variable
  overrides via `ADVANDEB_MCP_*`.
- Round-robin balancing, connection pooling, circuit breaker, retry —
  the resilience primitives expected of a gateway are present.
- README documents the protocol, REST endpoints, and configuration
  comprehensively.

### 6.2 Issues

- **No auth on the gateway.** Documented as intentional (it's "internal
  background service") but it binds to `0.0.0.0:8080` by default. Verify
  the production firewall actually drops external traffic to 8080. A
  bound-loopback default (`127.0.0.1:8080`) would be safer.
- **README claims 67 tests** — not verified in this review. Worth a
  `cargo test` run as a regression baseline.
- **Workflow context resolution** (`workflow/context.rs:157` LOC,
  `executor.rs:269` LOC) uses string templating (`{{step0.result}}`).
  Document the templating grammar — this is the kind of thing that
  silently breaks when types change.
- **No graceful shutdown wiring visible in `serve()`** — `axum::serve`
  blocks forever. Production restarts will drop in-flight WebSocket
  sessions hard. Add `with_graceful_shutdown` listening on `SIGTERM`.

externally observable and low-cost come first; deep refactors come last.

### P0 — Ship-blockers (this week)

1. **Fix JWT type confusion (S1 / B1).**
   In `core/auth.py::verify_token`, after decoding, raise 401 if
   `payload.get("type") == "refresh"`. Tag new access tokens explicitly
   with `"type": "access"`.

   Either (a) move `/health` into a dedicated router that the upstream
   proxy whitelists, or (b) add `/api/health` as the canonical endpoint

   `"your-secret-key-here"` or is shorter than 32 chars.
